## 3. C134 — “안내도 없음” 정정, 실제 화면 확인 범위

운영 메인 주소를 익명 GET으로 요청해 HTTP 200을 확인했다. 현재 전달되는 HTML에는 다음 요지의 안내가 이미 있다.

- 제목: **계정 및 개인 자료 삭제 안내 · 자동 삭제 기능 미제공**.
- 계정 탈퇴 및 개인 자료 자동 삭제 기능을 제공하지 않음.
- Neon Auth 계정만 삭제해도 별도 계획·일기·관찰 기록이 함께 삭제된다고 보장할 수 없음.
- 전체 데이터 내보내기로 먼저 백업하고, 안전한 삭제 절차 확인 전에는 인증 계정만 단독 삭제하지 말 것.
- 안내 자체가 삭제 요청을 처리하거나 삭제 완료를 보장하는 기능이 아님.

따라서 “현재 계정 삭제 기능·안내 모두 없음”은 정확하지 않다. **운영 HTML에 정확한 안내가 있음**은 실측했다. 그러나 안내는 로그인 후 다이어리 영역 안에 있고, 현재 연결로는 기존 사용자 세션의 실제 화면을 열지 못했다. 화면에서 보이고 펼쳐지는지까지 확인했다고 표기하지 않는다.

C134는 사용자가 제시한 기준에 따라 **정확한 자료 처리 안내 대안**으로도 판단할 수 있다. 이 대안의 화면 확인을 위해 실제 계정을 삭제할 필요는 없다. 별도로 PR #6의 계정 삭제 UI/API와 PostgreSQL 검사는 구현됐으나 관리형 Auth 실삭제와 Preview 전체 검증은 여전히 미완료다. 두 경로를 혼동하지 않는다.

## 4. 관리형 서버의 실제 해시 알고리즘 설정 — 외부 근거 부족 유지

운영 브랜치의 관리형 Auth 설정을 새로 조회했다. 이메일/비밀번호 사용 여부와 가입/메일 검증 등의 필드는 있지만 **해시 알고리즘·hash/verify 커스텀 여부 필드는 없었다.**

기존 Better Auth 기본 scrypt 문서·161자 저장 형식·솔트 차이 실측 근거는 유지한다. 그러나 그 근거를 특정 운영 인스턴스의 내부 설정 직접 증명으로 바꾸지 않는다. PostgreSQL의 DB 로그인용 `password_encryption` 설정도 앱 사용자의 Neon Auth 해시 알고리즘을 증명하지 못한다.

사용자가 일반 Members 메뉴나 SQL Editor에서 이 설정을 찾아야 하는 작업으로 넘기지 않는다. 직접 설정 증거가 필수라면 Neon이 해당 인스턴스의 알고리즘/커스텀 여부를 확인해 주는 제공자 근거가 필요하다. 이번 작업은 외부 문의를 보내지 않았다.

## 7. 비밀정보 감사 — 추가 검사 완료와 불가능한 전수 보증 구분

### 실제 이번에 수행한 범위

- 새로 fetch한 원격 브랜치 **10개**, 모든 로컬 참조에서 도달 가능한 **206개 커밋**의 고유 텍스트 blob **240개**를 검사했다. 당시 binary 제외 **0개**.
- 고신뢰 패턴: GitHub/AWS/Stripe/OpenAI 키 형태, PEM 개인키, JWT, 비밀번호를 포함한 DB/캐시 접속 URI. **검출 0건**. 스캐너: [audit-secrets.py](../scripts/audit-secrets.py).
- 소스의 `console` 호출과 응답 경로를 검토했다. 추가 회귀 검사에서 제공자 성공/실패 payload 및 예외에 **가짜 민감정보 sentinel**을 넣었을 때 인증 핸들러의 반환 JSON·애플리케이션 로그에 그 문자열이 나오지 않음을 확인했다. 실제 비밀정보는 테스트에 쓰지 않았다.
- 현재 공개 증거의 마스킹 표기·원본 미보존/재구성 구분을 검토했다.
- `npm run check`: **38개 통과, 실패 0개**. 앞선 36개에 실제 관찰값 표시 검사와 인증 응답/로그 회귀 검사를 추가했다.

### 확인하지 못한 범위

- Vercel의 Production 최근 1시간 Runtime Logs조차 현재 연결에서는 403으로 실패했다. **오류는 로그 0건이 아니다.** 전체 기간·다른 표현 검색을 수행했다고 기록하지 않는다.
- 이전 2026-10-18 최근 1시간 로그 실측은 과거의 한정된 근거다. 보존 기간 밖 로그를 소급 복구하거나 모든 표현·인코딩을 검사한 것은 아니다.
- 일반 문자열 할당·분할/인코딩·이미지·외부 제출 플랫폼·모든 브라우저 Network를 포괄하는 전수 보증은 하지 않는다. 패턴 검사는 한정된 검사다.

### Network 점검 표현 정정

브라우저 본인의 DevTools에서 로그인 요청 Payload의 비밀번호, 인증 요청 Cookie, 세션 발급 응답 Set-Cookie가 보이는 것은 인증 흐름에서 정상일 수 있다. **“Network 어디에도 비밀번호/쿠키/토큰 원문이 보이지 않아야 한다”는 조건으로 끝없이 확인하면 안 된다.**

구분할 것은 HTTPS 보호, HttpOnly/Secure/SameSite, 불필요한 응답·로그·화면에 자격증명을 되돌려 주지 않는지, DB 비밀키가 프런트로 전달되지 않는지, 외부 제출 캡처의 원문을 가렸는지다. 이 설명은 모든 해당 항목의 실제 브라우저 검증을 완료했다는 뜻이 아니다. 원본 HAR에는 인증 비밀이 포함될 수 있으므로 공개 GitHub에 업로드하지 않는다.

## Vercel 접근 혼란에 대한 정확한 상태

사용자의 계정은 Owner이며 연결된 계정도 일치하지만 팀 목록/프로젝트/로그 접근이 403이다. 서비스 오류는 팀 승인 링크 발급 기능을 안내하나 현재 노출된 도구에는 그 기능이 없다. 현재 환경에 인증된 Vercel CLI도 없다.

**Members 변경이나 ChatGPT “모든 도구 허용” 변경을 해결 절차로 안내하지 않는다.** 후자는 에이전트 작업 승인 정책이며 Vercel 팀 접근 grant를 추가하지 않는다. 확인되지 않은 버튼을 찾아보라고 반복 요청하지 않는다. 이 제한은 GitHub/Neon 읽기 검증까지 막는 문제가 아니므로 가능한 작업을 이번에 완료했다.
