## 4. 비밀번호 저장/솔트 (2026-10-17 사용자 실측)

Neon Auth `neon_auth.account`의 `providerId='credential'` 데이터로 읽기 전용 집계.

| 항목 | 실측 집계 |
| --- | --- |
| 당시 credential 계정 | 3 |
| 당시 계정별 저장 문자열 길이 | 161자(각 계정) |
| 패턴 | `^[0-9a-f]{32}:[0-9a-f]{128}$` |
| 당시 서로 다른 솔트 | 3 |
| **같은 시험용 비밀번호를 사용한 서로 다른 계정** | `account_count=2` |
| 저장값 구별 | `distinct_hash_count=2` |
| 솔트 구별 | `distinct_salt_count=2` |

입력 비밀번호 원문·실제 161자 해시 문자열·솔트 원문은 저장소에 싣지 않습니다. 위 집계는 다른 솔트/저장값이 생성됐다는 실측 증거입니다. Better Auth 기본 해시 알고리즘은 **scrypt**이지만 이 집계만으로 관리형 Neon Auth 운영의 내부 설정을 단정하지 않습니다.

## 9. T07-C123 — URL·헤더·본문 계정 ID 변조 실제 운영 검사 (2026-10-18)

| 테스트 | 운영 실측 결과 | 판정 |
| --- | --- | --- |
| 계정 1의 본인 GET 목록과 URL `user_id=[B]` + 헤더 `X-User-Id: [B]` 주입 GET 비교 | 변조 GET **HTTP 200**, `본인 목록 유지: true`, 원래 목록 **2건** | **PASS** |

**계정 2의 건수가 별도로 1 → 2건 증가한 원인 검토:** 사용자가 나중에 보고한 계정 2의 추가 기록은 **2026-10-18 14:03:38 KST**, 계정 1의 Console POST로 생성된 계정 1의 추가 기록은 **14:04:55 KST**에 각각 생성됐음을 운영 Neon의 `pds_plans.created_at` 및 `user_id`만으로 확인했습니다. **B 추가 기록이 A 추가 기록보다 1분 17초 먼저 생성**됐으므로, 뒤에 실행된 A의 해당 POST가 B의 기록까지 만들었다는 주장은 시간 순서와 맞지 않습니다. 다만 B 기록 생성의 정확한 입력 경로(버튼/요청/탭)는 DB 생성 시각만으로 확인할 수 없습니다. 원래 B가 1건이었다는 이전 응답과 이후 2건이라는 응답은 모두 실제로 보고됐고, 혼동을 방지하기 위해 그대로 남깁니다.

**결론:** C123의 계정 1 URL·헤더·본문 변조 실측은 통과. 이 검사는 **실제 다른 계정 소유 레코드 수정·삭제 거절 시점의 건수 불변(C122)** 증거와는 별개입니다. 기존 C122 관련 과거 404 6건을 재실행하지 않았습니다.

| 계정 1 → 계정 2 소유 ID: `DELETE /api/ownership-test` | **404** | 거절 |
| 계정 2 → 계정 1 소유 ID: `PATCH /api/ownership-test` | **404** | 거절 |
| 계정 2 → 계정 1 소유 ID: `DELETE /api/ownership-test` | **404** | 거절 |

**판정: T07-C122 실측 통과.** 양쪽 타인 수정·삭제 시도는 HTTP 404로 거절됐으며, 전후 2계정의 모든 계획 수 및 검사 기록 상태 지문이 일치하여 **검사 대상 기록에 변화가 없음을 실제 DB 집계로 확인**했습니다. 이 검사는 앞서 확인된 양방향 타인 `GET` 404를 재실행하지 않았습니다.

**범위:** 검증 기간 동안의 `pds_plans` 전용 검사 기록 상태와 행 개수 비교입니다. 모든 13종 개인 기록 데이터의 내용 지문을 전수 비교한 검사는 아닙니다. HTTP 상태는 사용자 직접 보고, DB 전후 집계는 연결된 Neon에서 확인한 결과를 합쳐 기술합니다.

## 11. T07-C105·C106 — Production Logs의 민감정보 검색 실측 (2026-10-18)

사용자가 Vercel `plandosee-web-diary2`의 **Request Logs** 화면에서 `Environment=Production`, `Timeline=Last hour` 설정을 확인했습니다. 검색어 없이 해당 범위의 요청 로그 **21건**이 표시된 화면을 제공한 뒤, 아래 두 표현을 **각각 따로 검색**해 결과를 보고했습니다.

| 실제 검색 | 범위 | 결과 | 범위 한정 판정 |
| --- | --- | --- | --- |
| `password` | Production, 최근 1시간 | **0건** | 해당 표현 미발견 |
| `session_token=` | Production, 최근 1시간 | **0건** | 해당 표현 미발견 |

## 12. T07-C114 — 비밀번호 변경 후 다른 브라우저 세션 무효화 실제 Preview 검증 (2026-10-18)

**검사 환경:** GitHub 브랜치 `task7-neon-integration`의 Vercel **Preview**, Neon 관리형 Auth 연동. 사용자가 승인한 **별도 시험 계정**으로 일반 Chrome과 시크릿 Chrome에서 각각 로그인했습니다. `Production`의 비밀번호 변경 기능을 활성화하지 않았습니다.

| 순서 | 사용자가 직접 확인한 HTTP/화면 결과 | 의미 |
| --- | --- | --- |
| 1. 변경 전, 시크릿 창 `GET /api/state` | **HTTP 200** | 기존 별도 브라우저 세션에서 인증된 개인 자료 API 요청 성공 |
| 2. 일반 창 비밀번호 변경 화면 | **변경 성공 메시지** | `/api/auth?action=changePassword` 테스트 기능으로 변경 성공 확인 |
| 3. 변경 후, 같은 시크릿 창 `GET /api/state` | **HTTP 401 Unauthorized** | 기존 시크릿 세션으로 보호 API 접근 차단 |

해당 Preview의 `api/auth.js`는 관리형 Auth에 `POST /change-password`를 중계하며, **`revokeOtherSessions: true`를 서버에서 강제**하고, 서버가 확인한 이메일을 시험용 계정 허용 목록과 비교합니다. 프런트엔드는 로그인된 세션을 확인한 후에만 비밀번호 입력 폼을 표시합니다.

**판정: T07-C114 '비밀번호 변경 후 다른 세션의 보호 API 접근 차단' 실제 브라우저 실측 통과.** HTTP 200→401은 사용자가 같은 시크릿 창에서 직접 확인해 보고한 결과입니다. 비밀번호·쿠키·세션 토큰·개인 JSON 본문을 공개 GitHub에 기록하지 않았습니다.

**범위 및 미확인:** 비밀번호 변경 작업을 진행한 일반 창의 세션 유지 여부는 별도 확인하지 않았습니다. 이 검사는 **세션 자연 만료(T07-C111)**와 다르며 실제 만료된 세션 쿠키를 이용한 401 검증은 여전히 미완료입니다.

**검사 종료 조치:** Vercel의 `task7-neon-integration` **Preview 전용** `PASSWORD_CHANGE_TEST_ENABLED`를 `false`로 변경하고 관리 API에서 저장값을 다시 확인했습니다. 환경변수는 새 배포에 적용되므로 재배포 및 최신 Alias 연결을 별도 확인합니다. 이전의 고유 배포 URL까지 자동으로 무효화됐다고 주장하지 않습니다. 일반 Production 설정은 변경하지 않았습니다.
