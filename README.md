- SQL: [neon/005_daily_journal_cards.sql](neon/005_daily_journal_cards.sql). **Vercel이 사용하는 동일한 Neon 프로젝트·운영 브랜치**의 SQL Editor에서 파일 내용을 한 번 실행한 후 신규 코드 배포. 기존 테이블 삭제·기존 내용 변경은 없습니다. `pds_runtime` 역할에 필요한 권한과 FORCE RLS를 부여합니다.
- 신규 저장: 한국 시간(Asia/Seoul)의 **서버 오늘 날짜**로 저장. 작성한 내용이 없으면 카드 생성 금지. 한 날짜에 한 장만 존재하고 같은 날 다시 저장하면 그날 카드만 갱신합니다. 다른 날짜의 글은 절대로 덮어쓰지 않습니다.
- `나의 기록`: 이전 주간 카드도 원래 작성일에 그대로 표시합니다. 새 날짜별 카드와 함께 월별로 보며, 수정·색상 변경은 해당 카드만 바꿉니다. 하루 글을 작성하지 않았다면 그 날짜의 **새 카드가 생성되지 않습니다**.
- 날짜별 카드는 개인 JSON 내보내기에 `dailyJournals`로 포함되며, 가져오기는 날짜 중복과 계정 소유를 확인합니다. 과거 백업의 누락된 `dailyJournals`는 빈 배열로 취급해 계속 가져올 수 있습니다.
- **기존에 덮어쓴 과거 문장의 복구와는 별도**입니다. 이전 주간 카드의 `created_at`은 남아 있어 날짜는 보존할 수 있지만, 예전 주간 카드를 재저장하여 덮어쓴 본문은 이 코드 변경만으로 되찾을 수 없습니다.

## 과제 6 → 과제 7: 구현 흐름

과제 6에서 설계한 **White & Blue**와 **plan.do.see / little by little.**을 유지했습니다.

- **PLAN:** 주간 계획, 우선순위 01~05, 할 일의 계획 연결 또는 독립 사용, 계획 수정 이력, 소프트 삭제, 연결 계획 우선순위 상속.
- **DO:** MON~SUN 주간 체크표, 날짜별 진행/막힘 기록, 시작·종료 시각으로 실행 시간 합계, 할 일별 **MY FIRST STEP**(2분 이내 시작할 수 있는 작은 첫 행동).
- **SEE:** 주간 돌아보기, **오늘의 작은 발견**, **다음에 다르게 해볼 것**, 주차별 줄노트 아카이브, 기록 근거를 열 수 있는 시간 집계.
- **시간 기록:** 파란색 실제÷예상 도넛과 100% 초과 민트색 외부 링, 계획/실제 범례, h/m 숫자, 실제−예상 차이의 +/− 부호, 보라색 막대. **시간 사용 비율은 목표 달성률이 아닙니다.** 사용자의 이미지 피드백을 받아 폰트 크기·링 두께·여백·세로 구분선 길이를 반복 수정했습니다.
- **과제 7 확장:** 가입·로그인·로그아웃, 서버 인증·계정별 데이터 분리, 기존 JSON 검사/계정별 가져오기, 개인 백업, 5일 관찰 일지, 양방향 접근 검사 도구.

이전 데이터와 사용자 계정은 마이그레이션 없이 운영 중인 Neon 서버에 유지되며, **2026-10-17 운영 도메인에서 로그아웃 → 기존 계정 재로그인 후 이전 기록 표시**를 사용자가 직접 확인했습니다.

## 인증 구현 설명서 ① 무엇으로 붙였나

**선택:** 직접 구현이 아닌 **관리형 인증 서비스 Neon Auth (Better Auth 기반)**.

- **auth-ui.js:** 브라우저의 로그인·가입·로그아웃 흐름, 인증 상태 확인, 인증 전에 자료 화면 잠금.
- **api/auth.js:** 이메일 가입/로그인/로그아웃/세션 조회를 Neon Auth 서버에 전달하고 쿠키를 처리하는 동일 출처 서버 프록시.
- **api/db.js:** 서버에서 인증된 계정 ID를 얻어 SQL 실행 역할과 개인 RLS 권한을 설정.
- **패키지 선언 버전:** @neondatabase/auth **0.6.0-beta**, @neondatabase/serverless **^1.0.0**, pg **^8.13.1** ([package.json](package.json)). Neon 관리형 인증 서비스 내부 버전은 저장소만으로 확정되지 않습니다.

### ② 왜 이 방법을 골랐나

비밀번호 원문과 해시·세션 서명·만료를 모두 직접 관리할 때 생기는 위험을 줄이고, 과제 6의 웹 다이어리에 계정 단위 인증을 연결하기 위해서입니다. 고려할 수 있는 다른 방법은 **직접 bcrypt/argon2와 세션 서버를 만드는 것**이지만, 공격 방어·로그아웃 무효화·비밀번호 복구까지 직접 보안 책임을 져야 하므로 선택하지 않았습니다. 기존 과제 6의 **무로그인 Supabase API를 그대로 두는 방식**도 개인 기록 비공개 요구와 맞지 않습니다.

**확인 필요:** 2026-10-17 SQL에서 계정별 서로 다른 솔트와, 같은 시험용 비밀번호로 가입한 두 계정의 서로 다른 저장값을 확인했습니다. 다만 관리형 인증의 실제 알고리즘(scrypt 여부), 세션 TTL, 비밀번호 변경 후 기존 세션 폐기는 별도 확인이 필요합니다. 해당 내용은 인증 서비스 실제 설정·저장된 값(비밀 부분 마스킹)·검사 결과로 보완해야 합니다.

#### 과제 제출용 증거 수집 순서 — 아래는 결과가 아닌 검사 지침

1. **미로그인:** 로그아웃 상태에서 GET /api/state → 기대 HTTP **401**. 단, GET /api/auth?action=session은 로그인 상태 확인용이므로 HTTP 200 + authenticated:false일 수 있습니다.
2. **로그아웃 후 이전 쿠키 재사용:** 2026-10-17 사용자가 로그인 상태에서 `GET /api/state`의 개인 JSON 표시를 확인하고, 로그아웃 전에 보관한 세션 쿠키를 로그아웃 후 복원하여 **Request Cookies** 전송을 확인했습니다. 이후 같은 GET 경로에서 **HTTP 401 Unauthorized**를 확인했습니다. 로그인 전 상태의 HTTP 200 수치 자체는 별도 Network 캡처가 없으므로 사용자 확인 JSON 조회 결과로 기록합니다. 쿠키·토큰 값은 **[REDACTED]** 처리합니다.
3. **A→B:** 2026-10-16 과거 대화에서 GET/PATCH/DELETE가 **각각 HTTP 404 not_found**임을 확인. 별도 제출용으로 당시 요청·응답의 마스킹된 전문과 전후 데이터 건수를 모아 보관.
4. **B→A:** 2026-10-16 과거 대화에서 반대 방향 GET/PATCH/DELETE도 **각각 HTTP 404 not_found**임을 확인. **2026-10-18 별도 C122 검증에서 거절 전후 DB 건수·상태 지문 불변 실측 완료**.
5. **목록/변조:** **2026-10-18 운영 목록 실측 완료(T07-C125)** — A 세션 GET 목록 HTTP 200·2건, B 세션 GET 목록 HTTP 200·1건, 두 목록에 공통 ID 0건([증거](evidence/task7-auth-verification.md)). **계정 1 세션의 URL·헤더·본문 사용자 ID 변조(C123)도 2026-10-18 운영 실측 통과**: GET HTTP 200·본인 목록 유지 true; POST HTTP 201, 계정 1 2→3건·본인 목록 존재 true. B의 별도 추가 기록은 A 추가보다 1분 17초 먼저 생성됨(DB 읽기 전용 확인). **C122도 2026-10-18 실측 통과:** A→B/B→A PATCH·DELETE 네 요청 모두 HTTP 404, DB 검사 전후 A 테스트 계획 3→3건·B 2→2건 및 양쪽 상태 지문 일치([증거](evidence/task7-auth-verification.md)).

실제 제출에는 **Asia/Seoul 날짜, 메서드·URL, 비밀을 가린 요청/응답, 실제 HTTP 상태, 거절 전후 건수**가 필요합니다. **기대값을 실제 실행 결과처럼 제출하면 안 됩니다.**

## 인증 구현 설명서 ⑥ 아직 못 막은 것

1. **비밀번호 무차별 대입:** 관리형 인증의 현재 운영 속도 제한·잠금 정책을 실측하지 않았습니다. 반복 로그인 시도에 대한 보호 정도가 미확인입니다.
2. **비밀번호 저장·세션 수명:** 2026-10-17 사용자가 Neon SQL Editor의 **읽기 전용 SQL**로 초기 계정 `total_users=3`, `total_accounts=3`, `credential_accounts=3`, `accounts_with_password_hash=3`, `distinct_password_values=3`, 저장값 길이 모두 161자를 확인했습니다. 이어 형식 검사는 `matching_format_count=3`, `distinct_salt_count=3`이었습니다. **T07-C104 별도 시험:** 같은 시험용 비밀번호로 가입한 두 계정의 이메일을 실제 값으로 대체해 조회한 결과 `account_count=2`, `distinct_hash_count=2`, `distinct_salt_count=2`를 확인했습니다. 따라서 **동일한 비밀번호에도 계정별 다른 솔트와 저장값이 생성됐다는 실측 결과를 확보했습니다**. SQL의 정규식 `^[0-9a-f]{32}:[0-9a-f]{128}$`과 저장값 길이는 기본 scrypt 형식과 일치하지만 운영 서비스의 실제 해시 구현은 별도 설정·문서로 검증해야 합니다. Better Auth는 기본적으로 scrypt를 사용하지만 운영 구성의 실제 알고리즘과 세션 TTL, 비밀번호 변경 뒤 이전 쿠키 폐기는 추가 증거가 필요합니다.
3. **두 계정 권한 침범:** A↔B 읽기·수정·삭제 6건의 404 거절은 2026-10-16 확인했습니다. **2026-10-18 C122 별도 실측에서 양방향 PATCH·DELETE 4건 모두 404, 검사 전후 DB 건수 및 상태 지문까지 일치함을 확인했습니다.** 채점용 개별 HTTP 전문의 비밀값 마스킹/증거 정리는 계속 점검합니다.
4. **개인 정보 권리:** 계정 삭제 기능 미구현 및 5일 관찰 자료가 현재 JSON 백업에서 빠지는 문제가 있습니다.
5. **관찰 규칙 의미:** '처리 규칙' 변경만으로는 '계획 규칙' 변경 요구와 차이가 있습니다.
6. **운영 관리:** 비밀번호 재설정·2차 인증·상세 보안 감사 기록 등은 서비스 지원 범위와 실제 설정을 추가 점검해야 합니다.
